Project Overview

In this group project, you will design and implement a small Smart Campus AI Planning System.

Each group will consist of 3 students.

The project focuses on three central course learning outcomes:

  • CLO2: Determine search strategies including blind and heuristic search.
  • CLO3: Illustrate the performance of local, global, and optimal search.
  • CLO4: Investigate Constraint Satisfaction Problems (CSPs).

The project is worth 20 marks in total.

The objective is not simply to produce working Python code. You are expected to demonstrate that you understand:

  • how an AI problem is represented;
  • why a particular search strategy is appropriate;
  • how search strategies differ in performance;
  • how a scheduling problem can be represented as a CSP;
  • how CSP heuristics and constraint propagation affect search;
  • how experimental evidence supports your conclusions.
ImportantCore assessment principle

A correct program is only part of the project.

Marks are awarded mainly for algorithmic reasoning, experimental analysis, interpretation, and demonstrated understanding.

Project Scenario

A university would like to build an AI-based system that can support two campus-planning tasks:

  1. Route Planning
    Find an effective route between campus locations while considering travel cost.

  2. Scheduling and Allocation
    Assign activities, courses, rooms, or events to available resources while satisfying a set of constraints.

Your group will develop both components and evaluate the AI techniques used in each one.

Part I — Campus Route Planner

Goal

Build a search-based route-planning system for a campus represented as a weighted graph.

A state represents a campus location, and an edge represents a possible movement between two locations.

Each edge must have a positive travel cost such as:

  • distance;
  • travel time;
  • congestion cost;
  • accessibility cost;
  • or another meaningful quantity.

Minimum Graph Requirements

Your graph must contain at least:

  • 10 distinct locations;
  • 15 weighted connections;
  • at least two alternative routes between important locations;
  • at least one case where the shortest path in number of edges is not the lowest-cost path.

Example locations could include:

  • Main Gate;
  • Library;
  • Engineering Building;
  • Computer Science Building;
  • Student Center;
  • Administration;
  • Cafeteria;
  • Sports Center;
  • Medical Center;
  • Parking Area.

You may use fictional campus locations.

Required Search Algorithms — CLO2

You must implement and compare:

  1. Uniform-Cost Search (UCS)
  2. A* Search

Your A* implementation must use a meaningful heuristic \(h(n)\).

The A* evaluation function is

\[ f(n)=g(n)+h(n), \]

where:

  • \(g(n)\) is the path cost from the start state to \(n\);
  • \(h(n)\) estimates the remaining cost from \(n\) to the goal.

Required Search Evidence

For at least one small search instance, your submission must include a manual or clearly presented search trace showing items such as:

  • expanded state;
  • current path cost;
  • frontier contents or priorities;
  • parent/path update;
  • goal detection.

You must also explain:

  • why UCS is an uninformed optimal search strategy;
  • why A* is an informed search strategy;
  • what information your heuristic uses;
  • whether your heuristic is intended to be admissible;
  • why UCS and A* may expand different numbers of states.

Part II — Search Performance Investigation

Goal — CLO3

Use controlled experiments to analyze the behavior and performance of the route-planning algorithms.

Do not report only the final path. For each test case, collect appropriate performance measures and use them to explain the behavior of each algorithm.

Required Experiments

Evaluate at least three different start-goal pairs.

At least one experiment must investigate the effect of the heuristic.

For example, compare:

  • UCS;
  • A* with \(h(n)=0\);
  • A* with your proposed heuristic.

You must explain the results.

Good analysis answers questions such as:

  • Which algorithm expanded fewer states?
  • Did both algorithms return the same optimal path cost?
  • Why did the heuristic change the search order?
  • Was the heuristic informative?
  • What happened when the heuristic became weaker?
  • What is the relationship between solution quality and search effort?

Optional Optimization Extension

Groups that complete the required search analysis early may add a small local-search optimization component.

Examples include:

  • selecting a good order for visiting several campus locations;
  • optimizing a simple facility-placement objective;
  • comparing hill climbing and random-restart hill climbing.

This extension is optional and does not replace any required component.

Performance Measures

Measure Meaning
Solution path Route returned by the algorithm
Path cost Total cost of the returned route
States expanded Number of states removed from the frontier and expanded
Maximum frontier size Largest number of pending states
Runtime Approximate execution time, when meaningful
WarningReporting numbers is not sufficient

A table such as

A*: 11 expanded states

is not an analysis.

You must explain why the difference occurred.

Part III — Campus Scheduling CSP

Goal — CLO4

Design a small campus scheduling or allocation problem and solve it as a Constraint Satisfaction Problem (CSP).

A CSP is represented as

\[ (X,D,C), \]

where:

  • \(X\) is the set of variables;
  • \(D\) is the set of domains;
  • \(C\) is the set of constraints.

Possible Scheduling Problems

You may model one of the following:

  • exam scheduling;
  • classroom allocation;
  • laboratory scheduling;
  • student activity scheduling;
  • meeting-room allocation;
  • instructor-timeslot assignment.

Minimum CSP Requirements

Your CSP must contain at least:

  • 6 variables;
  • at least 3 possible values in the main domain;
  • at least 8 meaningful constraints;
  • at least one situation where a poor search choice causes unnecessary backtracking.

Examples of constraints include:

  • two courses cannot use the same room at the same time;
  • an instructor cannot teach two classes simultaneously;
  • a laboratory course must use a laboratory room;
  • two exams with common students cannot share a timeslot;
  • a particular activity is unavailable during one timeslot.

Required CSP Methods

You must implement:

  1. Backtracking Search
  2. MRV — Minimum Remaining Values
  3. Degree Heuristic as an MRV tie-breaker
  4. LCV — Least-Constraining Value
  5. Forward Checking

Your system should allow you to compare more than one configuration.

For example:

  • plain backtracking;
  • backtracking + MRV;
  • MRV + degree + LCV;
  • MRV + degree + LCV + forward checking.

Required CSP Evidence

Your report/notebook must clearly identify:

Variables

Example:

\[ X=\{C_1,C_2,C_3,\ldots\} \]

Domains

Example:

\[ D(C_1)=\{\text{S1},\text{S2},\text{S3}\} \]

Constraints

State the constraints formally or clearly in natural language.

You must also include at least one manual reasoning example showing:

  • current partial assignment;
  • remaining domains;
  • MRV choice;
  • degree tie-breaking when applicable;
  • LCV reasoning;
  • forward-checking reductions.

CSP Performance Analysis

Compare at least two solver configurations. Use the measures listed below and explain why heuristics and forward checking can reduce unnecessary search.

CSP Performance Measures

Measure Meaning
Assignments tried Candidate variable-value assignments tested
Consistency failures Assignments rejected by constraints
Backtracks Number of failed recursive branches
Domain wipeouts Empty domains detected by propagation
Maximum search depth Deepest partial assignment reached

Part VI — Live Understanding Check

During the demonstration, the instructor may change a small part of the problem and ask the group to predict the effect before running the code.

Examples include:

Search

  • increase one edge cost;
  • remove one connection;
  • change the start or goal;
  • weaken the heuristic;
  • set \(h(n)=0\).

CSP

  • remove one timeslot;
  • add one conflict constraint;
  • restrict one variable’s domain;
  • disable MRV;
  • disable forward checking.

Students may be asked:

Which algorithmic behavior do you expect to change, and why?

or:

Predict the next variable selected by MRV before running the solver.

The objective is to evaluate understanding rather than memorized code.

Part VIII — What Strong Projects Demonstrate

A strong project does more than run successfully.

It demonstrates that students can:

  • select an appropriate AI representation;
  • implement search algorithms correctly;
  • reason about heuristic search;
  • measure algorithmic performance;
  • explain experimental results;
  • formulate a real problem as a CSP;
  • use CSP heuristics appropriately;
  • identify why backtracking occurs;
  • explain the effect of forward checking;
  • make predictions before execution;
  • defend design decisions during the demonstration.

Part IX — Common Mistakes to Avoid

Avoid the following:

  • submitting code without explanations;
  • comparing algorithms on only one trivial instance;
  • reporting runtime only;
  • using an A* heuristic without explaining what it represents;
  • claiming a heuristic is admissible without justification;
  • defining a CSP without clearly identifying \(X\), \(D\), and \(C\);
  • using MRV, LCV, or forward checking without explaining their purpose;
  • showing results without interpreting them;
  • assigning one member all coding work and another member all writing work;
  • presenting a system that group members cannot explain.
